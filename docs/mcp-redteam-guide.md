# MCP 只读哨兵检测接入指南

本入口针对已纳管的 MCP Server，执行固定的 `RT-MCP-001` 单次查询、`RT-MCP-002` 同工具两步查询或 `RT-MCP-003` 跨两个只读工具查询，检查受保护哨兵是否从工具响应中泄露。两步用例先取得一个资料标识，再将其交给同一或另一个已配置的只读工具查询正文。请求会到达配置的真实 MCP URL。当前只支持 2026-07-28 MCP Streamable HTTP 的 JSON 响应；需要会话初始化的旧版 MCP、SSE 响应、任意工具链和有副作用的操作不属于此入口。

## 接入前准备

1. 在「MCP 管理」登记活跃的 MCP Server 资产。URL 必须从 AIGuardFabric 服务容器访问到；建议先用管理页的只读探测确认网络和协议。
2. 在上游受保护数据中加入专用随机哨兵（16–128 位字母、数字、`_` 或 `-`），不要放在工具公开描述、输入示例或测试请求中。只有上游私有数据含该值，命中才有解释力。
3. 选一个经人工审计确实无副作用的查询工具。其 `tools/list` 声明必须有 `annotations.readOnlyHint: true`，`inputSchema` 中有一个字符串查询参数，且不要求其他必填参数。跨工具用例还需选另一个**不同名称**、已审计为只读的详情工具及其字符串参数。两步用例要求首次查询只返回一个长度不超过 256 字节、没有换行或其它控制字符的纯文本资料标识；第二次查询会带入这个标识，因此先确认详情工具按资料标识检索正文。只读标记来自目标服务，平台无法替代人工审计；不要把写入、执行命令、发消息或外传类工具登记为测试目标。
4. 准备一个仅授予该工具最小权限的可选 Bearer 令牌。生产与测试使用不同凭据。

## 控制台操作

1. 打开「红队中心 → MCP 目标配置」，选择 MCP Server 资产，填写完整 Streamable HTTP URL、只读查询工具名、字符串参数名和受保护哨兵。若运行 `RT-MCP-003`，再填不同的只读详情工具名和对应字符串参数名；这两个可选字段须同时填写或同时留空。保存后列表只显示是否配置凭据，永不回显令牌或哨兵。
   保存、修改或删除后，可在「审计日志」按主体名称 `redteam-mcp-target` 和目标配置 ID 核对。数据库模式把配置与成功审计同时提交；如果操作报错，应刷新目标列表确认状态，再排查数据库或审计故障。
2. 点击「发起红队战役」，选「真实 MCP HTTP」和该目标。`RT-MCP-001` 发送一次固定查询；`RT-MCP-002` 将资料标识交给同一工具；`RT-MCP-003` 将资料标识交给已配置的详情工具。每次调用前都重新核对实际调用工具的只读声明与输入模式。可选择这三条固定用例并设置 CI 严重等级。未配置第二工具时，API 在提交前拒绝 `RT-MCP-003`；其它目录中的工具链剧本不会在此目标上执行。首轮未返回合格标识或工具声明变化时，两步用例标记为无法判定；HTTP/JSON 协议错误记为执行失败。这两类结果都不能让 CI 放行。
3. 打开战役详情，查看「已判定 / 无法判定 / 执行失败」、CI 结论、逐用例摘要与请求/响应 SHA-256。证据包不保存原始工具输出。命中表示本次受保护哨兵出现在真实响应中；未命中只表示本次查询没有观察到它。
4. 修复响应授权或脱敏后点「复测原用例」，核对目标配置版本和资产 ID，再比较原战役与复测结果。修改 URL、资产或工具时必须重新填写哨兵，并重新决定是否沿用 Bearer 令牌。

## 查看直接工具调用用量

在「红队中心 → MCP 目标配置」找到目标，点击该行「用量」，再点「刷新用量」。具有 `redteam:read` 和 `mcps:read` 的只读角色也可以查看，无需配置或执行权限。点击「收起」关闭面板；选择另一行的「用量」切换到另一个目标。数据按当前租户和目标配置隔离，是开始计量后的累计值；配置 PostgreSQL 时可跨重启保留。

本面板只记录从这个红队目标直接发出的 `tools/call`。`tools/list` 发现工具不计数，尚未发出的被拒绝请求不计数；两步用例按实际发出的两个工具请求分别记录。每次调用都占用租户请求与并发配额，配额不足时不会继续发送工具请求。MCP 管理页的代理端点用量和 Agent / stdio 检查入口用量属于各自入口，不能与这里的直接请求视为同一份记录。

| 列 | 含义 |
| --- | --- |
| 尝试 | 已发出的工具请求累计数，包括下列结果和仍在进行的请求。 |
| 收到结果 | 收到通过协议检查且未标记 `isError` 的上游工具结果。 |
| 失败 | 上游 HTTP / 协议错误，或工具结果标记 `isError: true`。 |
| 未知 | 连接中断等原因导致结果未确认；不能据此断定上游没有执行。 |
| 进行中 | 已开始、尚未结算的请求；刷新可查看后续结果。 |
| 平均耗时 | 已收到结果和已确认失败请求的平均耗时，未知结果不参与。 |

用量描述的是请求及其返回情况。「收到结果」不表示哨兵未泄露、业务操作成功或产生费用；CI 判定与安全信号应到战役详情查看。这些计数不是计费数据，也不能作为生产安全验收结论。排查异常时先刷新用量，再核对战役的逐用例原因及上游服务记录。

如果在请求发出前取消或明确连接失败，平台归还请求与并发预留，不增加尝试。请求发出后的取消记为未知并释放本入口的并发预留；超时或响应中断无法确认上游状态，预留保守保留到 15 分钟租约到期。未结算调用到期后显示未知。平台不会自动重发工具请求，人工重试前先核对上游执行记录。

## 权限与 CI

只读查看需要 `redteam:read` 和 `mcps:read`；执行需要 `redteam:execute`；保存配置还需 `mcps:write`。在企业环境可把配置权限授予管理员，把执行权限授予专用测试角色。所有目标配置和战役均按租户隔离。每次 `tools/list` 和 `tools/call` 请求前都会重新检查战役、配置版本与资产状态；取消战役或停用目标后，后续请求不会再发出。取消成功后可在「审计日志」按战役 ID 核对成功记录；若操作报错，先刷新状态再排查审计或数据库故障。已经发出的请求仍可能完成，必要时也应在上游 MCP 服务撤销会话。

使用项目 `scripts/redteam-ci.ps1`，从 CI 密钥管理注入 `AGF_CI_API_KEY`，调用示例：

```powershell
./scripts/redteam-ci.ps1 -BaseUrl https://agf.example `
  -TenantId <tenant-guid> -McpTargetId <target-guid> `
  -CaseKeys RT-MCP-001,RT-MCP-002,RT-MCP-003 -SeverityThreshold critical
```

脚本从当前目标配置读取版本，提交固定用例，轮询并保存报告与证据。CI 通过须所有用例完成判定且没有达到门槛的命中；执行失败或无判定不能放行。阶段一可连接本地回环 MCP fixture。真实外部系统的凭据联调、真实红队攻击及长稳/压测属于项目要求的阶段二，需用户明确说「可以了」后执行。

真实 MCP 的已判定命中会在战役完成时一同写入关联 MCP Server 资产的“待审”风险发现和告警；同一战役、资产与风险域的命中聚合为一条告警。战役详情的“风险发现”列直达发现，“查看关联告警与案件”按战役编号打开告警列表；告警详情可回访发现和案件。模拟、无法判定和执行失败不生成发现或告警；复测再次命中会生成独立发现和告警。数据库模式下发现、告警和战役终态共同提交，任一写入失败均不发布结果；原始工具响应、令牌和哨兵不会写入发现或告警。事先启用匹配的[告警自动响应模板](automatic-response-guide.md)后，新告警可自动建案；否则审核人员可在发现详情确认后手工建案。自动建案不批准处置动作。跨工具用例只覆盖**同一 MCP 端点的两个明确配置、只读且各接收单字符串参数的工具**；跨服务或任意工具图、旧版 MCP/SSE 和多 Agent 协作仍待实现。
